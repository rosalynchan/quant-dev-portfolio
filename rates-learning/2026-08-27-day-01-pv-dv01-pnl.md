# From Present Value to DV01 and Daily PnL: A Front-Office Developer’s Mental Model

## Abstract

Present value, DV01, and daily PnL are often delivered by different services and displayed in different screens, but they belong to one valuation chain. This article builds a practical mental model for that chain, shows where a linear risk estimate diverges from full revaluation, and translates a trader's apparently simple request into an auditable engineering contract.

## Desk Context

A GBP Rates trader asks:

> “Can you show me yesterday's PnL and current DV01? The book looks down after rates sold off.”

A useful answer requires more than two numbers. The developer must establish the position population, valuation window, market-data snapshots, risk convention, currency, units, and PnL components. Without those definitions, a numerically correct calculation can still be operationally wrong.

The core chain is:

[
\text{trade economics} + \text{valuation context}
\longrightarrow PV
\longrightarrow risk
\longrightarrow PnL\ explain
]

## Present Value Is Context-Dependent

For deterministic cash flows, present value can be written as:

[
PV = \sum_i CF_i \times DF(t_i)
]

The formula is compact; the production state behind it is not. A reproducible PV depends on the trade economics and an explicit valuation context, including:

- valuation timestamp and market-data cut;
- discount and projection curves;
- fixing set;
- day-count, calendar, and business-day conventions;
- collateral or CSA assumptions;
- model and market-data versions;
- reporting currency.

This is why an API such as `price(trade_id)` is underspecified. If the valuation context is implicit, an investigation cannot reliably reproduce yesterday's number.

## DV01 Turns a Rate Move into Money

DV01 measures the change in PV for a one-basis-point increase in rates. A transparent bump-and-revalue definition is:

[
DV01_{signed} = PV(curve + 1bp) - PV(curve)
]

For a long fixed cash flow, higher rates reduce present value, so signed DV01 is normally negative.

However, the label “DV01” is not a complete specification. A desk may mean:

- signed PV change or positive risk magnitude;
- currency amount per basis point or derivative per unit rate;
- parallel or bucketed sensitivity;
- local or reporting currency;
- clean or dirty valuation.

Units and sign conventions should be fields in the data contract, not tribal knowledge encoded in a dashboard label.

## Worked Numerical Example

Consider a simplified cash flow paying GBP 10,000,000 in five years. Assume a flat annual discount rate of 4%.

[
PV_0 = \frac{10{,}000{,}000}{(1.04)^5}
     = GBP\ 8{,}219{,}271.07
]

Bump the rate by one basis point to 4.01%:

[
PV_{+1bp} = \frac{10{,}000{,}000}{(1.0401)^5}
          = GBP\ 8{,}215{,}320.63
]

Therefore:

[
DV01_{signed} = -GBP\ 3{,}950.43
]

If the rate rises by 7bp, the linear estimate is:

[
PnL_{linear} \approx -3{,}950.43 \times 7
                   = -GBP\ 27{,}653.03
]

A full revaluation at 4.07% gives:

[
PV_{4.07\%} = GBP\ 8{,}191{,}665.83
]

and:

[
PnL_{full} = -GBP\ 27{,}605.24
]

The GBP 47.79 difference is a small convexity residual. For a real swap portfolio, the gap can also reflect non-parallel curve moves, cross-effects, fixings, time decay, trade activity, and cash flows.

The practical conclusion is important: **DV01 multiplied by the observed move is a fast sanity check, not a complete daily PnL calculation.**

## From Valuation Difference to PnL Explain

At its simplest:

[
Daily\ PnL = PV_{today} - PV_{yesterday}
]

A desk-ready explain usually decomposes that difference:

[
Total\ PnL =
Market\ Move + Carry/Theta + New\ Trades + Amendments
+ Cash/Settlements + Fixings + Fees + FX + Residual
]

The bridge is meaningful only when its endpoints are controlled. Common alignment failures include:

- yesterday uses an official close while today uses an arbitrary live snapshot;
- one side contains a different trade population because a feed is late;
- one valuation uses a newly published fixing and the other does not;
- PV is stored in currency units while a dashboard renders risk in thousands;
- pricing and risk jobs resolve different curve versions.

These often present as quantitative discrepancies but are fundamentally state, lineage, or contract problems.

## Engineering Design

Make the valuation context immutable and referenceable:

```python
@dataclass(frozen=True)
class ValuationContext:
    as_of: datetime
    market_data_cut: str
    curve_id: str
    curve_version: str
    fixing_set_id: str
    model_version: str
    reporting_currency: str

@dataclass(frozen=True)
class RiskResult:
    trade_id: str
    pv: float
    dv01_signed: float
    currency: str
    amount_unit: Literal["CCY"]
    bump_bp: float
    risk_type: Literal["PARALLEL", "BUCKETED"]
    valuation_context_id: str
```

A deliberately explicit bump-and-revalue implementation might look like this:

```python
def pv_and_dv01(trade, curve, context):
    validate_curve_matches_context(curve, context)

    base_pv = price(trade, curve, context)
    bumped_pv = price(
        trade,
        curve.parallel_bump(bp=1.0),
        context,
    )

    return RiskResult(
        trade_id=trade.id,
        pv=base_pv,
        dv01_signed=bumped_pv - base_pv,
        currency=trade.currency,
        amount_unit="CCY",
        bump_bp=1.0,
        risk_type="PARALLEL",
        valuation_context_id=context.id,
    )
```

For PnL explain, preserve both endpoint identities and each transformation:

```python
class PnLExplain:
    opening_context_id: str
    closing_context_id: str
    opening_population_hash: str
    closing_population_hash: str
    market_move: float
    carry_theta: float
    trade_activity: float
    cash_and_settlements: float
    fixing_effect: float
    fx_effect: float
    residual: float
    currency: str
```

A stable API should return business results and diagnostics separately. A partial calculation with rejected trades must not look like a complete zero-risk result.

## Data Quality, Controls, and Production Failure Modes

Useful pre- and post-calculation controls include:

```python
assert risk.bump_bp == 1.0
assert risk.currency == requested_reporting_currency
assert opening.market_data_cut == "LONDON_CLOSE"
assert market_revaluation.population_hash == opening.population_hash
assert abs(total_pnl - sum(explain_components)) < configured_tolerance
```

Production observability should expose:

- snapshot, curve, fixing, model, and calculation-run identifiers;
- expected, processed, rejected, and stale trade counts;
- missing or stale curve nodes;
- queue lag, runtime, and last successful valuation timestamp;
- top PnL contributors and unexplained residual;
- idempotency keys for retries.

Three failures deserve particular attention.

First, **silent fallback**: a missing live curve is replaced by yesterday's curve without an explicit status. The screen looks healthy but risk is stale.

Second, **population drift**: a delayed trade feed changes the book between the opening and closing valuations. Market PnL is contaminated by activity or missing-trade effects.

Third, **semantic drift**: a service changes DV01 from signed currency-per-bp to positive thousands while downstream consumers continue to interpret the old schema. Schema validation alone will not catch a business-semantic break; versioned contracts and reconciliation tests are required.

## Requirement Discovery on the Desk

When a trader asks for “today's PnL and risk,” clarify:

1. Which book, legal entity, and trade population are in scope?
2. Is the window close-to-close, close-to-live, or between named snapshots?
3. Is DV01 signed or absolute, parallel or bucketed?
4. What are the currency, amount unit, curve family, and bump convention?
5. Should today's new and amended trades be included, and how should they be separated?
6. Which explain components are required?
7. What residual threshold should trigger investigation?
8. What granularity, refresh frequency, and latency are operationally useful?

A concise requirement translation could be:

```yaml
scope: GBP_RATES_BOOK
pnl_window: previous_official_close -> current_live_snapshot
population:
  market_move: opening_frozen_population
  activity: intraday_new_and_amended_trades
risk:
  measure: bucketed_dv01
  sign: signed_pv_change_for_plus_1bp
  unit: GBP_per_bp
controls:
  residual_alert_threshold: GBP_10000
output_granularity: [book, curve, tenor_bucket, trade]
```

This turns “which rate move caused the loss?” into definitions that engineering, quant, and trading can test together.

## Interview Questions

- Why can DV01 explain the direction of PnL but fail to reproduce the exact amount?
- How would you separate market PnL from intraday trade activity?
- Which identifiers are necessary to reproduce a historical valuation?
- How would you detect a risk job that completed successfully but processed only 97% of the book?
- What contract change would prevent a signed-versus-absolute DV01 misunderstanding?

Strong answers connect quantitative intuition to operational controls: local linear approximation, frozen populations, immutable contexts, completeness metrics, explicit units, and versioned semantics.

## Key Takeaways

- PV is a function of trade economics and an explicit valuation context.
- DV01 is a local monetary sensitivity; it is not complete PnL.
- A useful PnL explain aligns valuation endpoints and separates market, time, activity, cash, fixing, FX, and residual effects.
- Sign, unit, currency, bump, and bucket definitions belong in the contract.
- Front-office credibility comes from reproducibility, lineage, completeness controls, and clear failure semantics—not merely from producing a number quickly.
